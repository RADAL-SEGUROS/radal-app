Radal · v12 · analysis before build

Partial journeys and three-level Cobranza,
with Forpay as the native rail

The journey stops being the product's backbone. A broker can start anywhere: a policy PDF, two portal quotes, or the full market process. After the policy, Cobranza is what the broker buys. How far Radal can take a cuota depends on the insurer behind it: native through Forpay, assisted (mail, reminders, insurer statements) or record only. This document covers what that means for the database, the backend, the frontend and the infrastructure.

Source: team spec “RADAL · Clic a clic” v15 (01-10-2026) CTO diagram “RADAL x Forpay” Code on dev @ 51ada38 (v11) Prior analysis: docs/plan-v12-tres-vias.md Web research: Forpay · Transbank · CMF · mail APIs

01The short version

1 · The journey becomes optional

The colocación stays the parent of every policy. The 12-stage machine gets entry points, and stages before the entry are marked omitida, which is the team's tres vías. The new part is that Cobranza no longer depends on the journey. The minimum path is Subir póliza → Confirmar datos → Plan de pago → Cobranza, and it never touches Antecedentes.

2 · One cuota, three levels

Each cuota gets a collection level, resolved at run time from its insurer, payment method and payer contact. Nativa · Forpay Asistida Registro. When an insurer goes live on Forpay, its open cuotas move up a level on their own. Nothing is migrated and no plan is rebuilt.

3 · Radal starts acting on its own

Up to v11 nothing in Radal runs without a click. v12 needs scheduled jobs (the cuota clock, reminders, mailbox polling, subscription renewals, UF rates) and inbound events (Forpay webhooks, Gmail and Graph push). That infrastructure doesn't exist yet.

The trap that would break the first webhook. Our API sits behind CloudFront OAC → Lambda Function URL, and OAC requires every POST to carry x-amz-content-sha256 (OAC constraint #2). Our SPA sends that header. Forpay, Google Pub/Sub and Microsoft Graph never will, so their POSTs would fail with InvalidSignatureException. Webhooks need their own ingress: an API Gateway HTTP API in front of a small Lambda that verifies the signature, writes to an inbox and enqueues. Section 11 has the details.

What “partial” means in practice

The team's v15 already defines the machinery (12 stages, 7 steps, 3 vías, R6/R34). The Operatividad table (R38) carries the idea furthest: every feature switches on when its data exists, and nothing is gated on having walked the journey. v12 applies the same rule to Cobranza, one rung at a time:

The ficha shows the missing rungs as the team's “Falta: X” line, for example “Falta: correo del pagador → sin avisos” or “HDI aún no está en Forpay (estimado 30-10) → cobro asistido”. These are never pop-ups or blockers. They are reasons the server returns, which keeps us within non-negotiable #3 (no dead buttons).

Your hypothesis, checked: “a payment link with enough metadata, money goes to the insurer's own account.” Right on the money flow and on the link. Two refinements:
(a) It is not a sub-account API. Forpay's API is single-company. For cards, one Radal Mall company creates links whose installments each name their insurer's Transbank child store. For PAC and TEF, expect one Forpay company per insurer (§04.4). In both cases settlement goes straight to the insurer, which keeps Radal and the broker out of the money (§05).
(b) The link itself carries the metadata. A OnePay link holds one installment per cuota, each with our cuota id as external id, the amount in UF with currencyConvert: TO_DAY (Forpay converts on the day of payment), the store's commerce code and free metadata. The UF drift problem is solved by Forpay. We still send payers to a Radal portal URL (/pay/{token}), and the portal creates the OnePay link when they click. That way one page covers Nivel 1 and Nivel 2 cuotas, a paid cuota can never be paid twice through an old link, and link expiry, which isn't documented, stops mattering.

04Forpay: what the developer docs say

We read all 41 pages of Forpay's public API reference (forpaydocs.readme.io), its embedded OpenAPI specs and its product pages. The verdict is below, followed by the evidence.

Forpay never touches the money

Forpay SpA (RUT 77.209.349-7) describes itself as a proveedor de servicios tecnológicos: “en ningún momento tocamos los dineros… viajan directamente de las cuentas o tarjetas bancarias de los clientes finales hacia las cuentas de las empresas” (FAQ). It has a product page for “compañías y corredoras de seguros”.

No sub-account API, but a Mall

The public API is single-company: credentials, commerce and login are tied to one RUT, and “la empresa no puede consultar datos de otro comercio”. There is no endpoint to onboard an insurer. The one documented multi-merchant mechanism is OnePay with isMall: true plus a Transbank child f_commerceCode on each installment. That covers cards and spot payments only.

Its model fits ours closely

Forpay is built around mandates with installments. Each installment has its own id, due date, amount in UF or CLP (currencyConvert: TO_DAY) and free metadata. That maps onto our plan de pago → cuotas almost one to one.

4.3 · Webhooks

  • Two URLs per mandate, passed in the create body: activationWebhook (mandate active or annulled; PAC state 11 “en confirmación banco”) and paymentWebhook (every charge attempt). There is no global webhook config.
  • The signature is not a header and not a raw-body HMAC. It is HMAC-SHA256 in Base64 over specific fields concatenated in a fixed order. The order differs by webhook type and payment method, and payment fields are included only once the installment is paid. Our verifier has to rebuild that string, using the HMAC key of the Forpay company that owns the mandate.
  • Retries on any non-2xx response. Count and backoff are not public. HTTPS only, with an IP allowlist on request.
  • Forpay recommends idempotency on installment.internalId + state.id, plus periodic polling for reconciliation.

The HMAC key differs per Forpay company, so our webhook URL has to say which company is calling: /forpay/{provider_account}/payment. Webhooks · HMAC · Buenas prácticas

4.4 · So, is it “just a sub-account thing”?

Commercially, yes: money goes to each insurer's own account and Forpay never holds it. Technically it isn't a sub-account API, and that shapes the integration:

Cards and spot payments: one Radal Mall

A single Forpay company, Radal's Mall, creates OnePay links with isMall. Each cuota's installment carries its insurer's Transbank child commerce code, so one checkout can split across insurers. Transbank states that “una plataforma SaaS puede ser un mall y las empresas clientes de la plataforma pueden ser” the stores, and that “la recaudación… irá directo al cliente” (Transbank). Each insurer still signs its own Transbank affiliation for its store code.

PAC and TEF: most likely one Forpay company per insurer

The docs give no way to route PAC or TEF to N insurers from one company. Expect either one Forpay company (credential set) per insurer, operated by Radal with the insurer's authorisation, or a multi-RUT setup that Forpay configures by hand. We model both as a provider_account row, and each insurer channel points to the account that collects for it. This is the first question for the Forpay meeting.

Not public: the production base URL, an SDK, link (Magic Link / OnePay) expiry, refund API, pricing, onboarding KYC and lead time, and what “Portal de Pagos 3A/3B” means. The CTO's fees (TEF 0.013–0.055 UF, PAC 0.04 + 0.025 UF, cards 1–2%) could not be confirmed publicly and presumably come from a Forpay quote.

06Three levels of Cobranza

The team's v15 has two horizons: MVP = registro and lanzamiento = avisos + plataforma + C6. v12 changes that sequence into three levels that coexist in the same broker, on the same day, on the same screen. Which level a cuota gets depends on its insurer. Brokers don't pick one.

NIVEL 0 · REGISTRO

Record & alert

  • Plan de pago, cuotas, manual payments, reversals, partial payments
  • Gestiones with Promete pagar el
  • Cuota clock: bell alerts to the ejecutivo at −15/−5/0/+3/+10, then Riesgo de término
  • PAC rechazado and Confirmar pago by hand
Available when: the policy has a plan. This is the team's MVP (C1–C4) unchanged.
NIVEL 1 · ASISTIDA

Remind, detect, reconcile

  • Avisos to the pagador (cc contratante) with the insurer's own payment instructions: its portal URL, bank account or coupon
  • Mailbox watch: transfer comprobantes, insurer receipts, PAC rejections and replies become suggestions to confirm
  • Insurer statement upload (C6) confirms many cuotas at once
  • Payer portal with “Ya pagué — subir comprobante”
Available when: the payer has an email or WhatsApp, and the insurer's payment instructions are known. Detection also needs a connected mailbox. This covers insurers not on Forpay yet, or never.
NIVEL 2 · NATIVA (FORPAY)

Collect natively

  • Every aviso carries a Radal portal link that turns into Webpay, OneClick, TEF or PAC checkout
  • Money settles directly to the insurer (store, account or convenio)
  • Webhook → payment confirmed by the rail, no human step
  • PAC/OneClick enrollment for recurring cuotas
  • Settlement reconciliation per insurer
Available when: the lead insurer (R18, coaseguro) has an active Forpay channel for the cuota's method and the broker has opted in.

The resolver: one function decides the level

The level is not stored on the cuota. It is computed whenever a notice is sent or a page is rendered, which is why an insurer going live in two weeks upgrades every open cuota without a migration. Brokers see the result as a badge with a Spanish reason.

backend/app/services/collection/resolver.py (sketch)
@dataclass(frozen=True)
class CollectionMode:
    level: Literal["record", "assisted", "native"]
    channels: tuple[PaymentChannel, ...]      # what the payer may use
    reason: str                               # Spanish, shown verbatim in the UI
    missing: tuple[str, ...]                  # "Falta: X" items, i18n keys


def resolve_collection_mode(cuota: CollectionInstallment, *, today: date) -> CollectionMode:
    plan, policy = cuota.collection_plan, cuota.collection_plan.policy
    insurer = policy.lead_insurer                      # R18: coaseguro pays the leader
    payer = policy.payer_party                         # pagador, defaults to contratante (R14)
    profile = insurer.collection_profile               # canonical, managed by Radal

    if payer is None or not payer.has_reachable_channel():
        return CollectionMode("record", (), "Falta contacto del pagador", ("payer_contact",))

    live = profile.active_channels_for(plan.payment_method) if profile else ()
    if live and policy.broker.native_collection_enabled:
        return CollectionMode("native", live, f"{insurer.short_name} cobra con Forpay", ())

    if profile and profile.payment_instructions:
        eta = profile.expected_live_on
        why = f"{insurer.short_name} aún no está en Forpay" + (f" (estimado {eta:%d-%m})" if eta else "")
        return CollectionMode("assisted", (), why, ())

    return CollectionMode("record", (), f"Sin instrucciones de pago de {insurer.short_name}",
                          ("insurer_payment_instructions",))

Privacy by design (Ley 21.719)

Radal must not become an archive of the broker's whole inbox. Recommended defaults:

  • Order of preference: a forwarding address (Radal sees only what is forwarded), then a shared collections mailbox (e.g. cobranza@corredora.cl), then personal inboxes.
  • A prefilter runs before anything is stored: sender domains of insurers and Chilean banks (maintained in insurer_collection_profile.sender_domains plus a bank list), subject keywords, PDF or image attachments.
  • Non-matching messages: keep the provider id only (for cursor and dedup) and no content.
  • Matched messages: the .eml and attachments become document rows (non-negotiable #8), retained per broker policy.
  • Tokens and passwords never go in table columns. Use Secrets Manager, KMS-encrypted, and store only the reference in a column.

Matching a comprobante to a cuota

score(evidence, cuota): deterministic and explainable; the AI only extracts
def score(ev: ExtractedEvidence, c: OpenCuota, rates: CurrencyRates) -> Match:
    reasons, s = [], 0.0
    expected_clp = c.amount_uf * rates.uf_on(ev.paid_on or ev.received_on)
    if ev.amount_clp and within(ev.amount_clp, expected_clp, pct=0.01, clp=1_000):   # team's ±1% or $1.000
        s += 0.45; reasons.append("monto calza con la cuota a UF del día")
    if ev.payer_rut and ev.payer_rut in c.party_ruts:            # contratante, pagador, asegurados
        s += 0.25; reasons.append("RUT del pagador es parte de la póliza")
    if ev.policy_number and normalize(ev.policy_number) == c.policy_number_norm:
        s += 0.20; reasons.append("menciona el n° de póliza")
    if ev.beneficiary_rut and ev.beneficiary_rut == c.insurer_rut:
        s += 0.10; reasons.append("transferencia a la cuenta de la compañía")
    if not (c.due_date - timedelta(days=20) <= ev.paid_on <= c.due_date + timedelta(days=45)):
        s -= 0.15; reasons.append("fecha lejos del vencimiento")
    return Match(c.id, round(s, 2), reasons)
# ≥ 0.70 and a unique best → "sugerido"; 0.40–0.70 → "revisar"; ties → the human chooses. Never auto-commit.

One ledger for every run

job_run(job, scheduled_for) is unique. A retried or duplicated EventBridge invocation inserts nothing new and exits. Every run stores counts and an error.

provider_event(provider, dedup_key) is unique. For Forpay the key is installment.internalId:state.id, as they recommend. Webhooks are stored before they are processed. Processing is a separate, retryable step, so replays are free and nothing gets lost when processing fails.

12.3 · The cuota state, computed (team rule 3, extended)

backend/app/services/collection/status.py: one pure function, used by the API, the clock and the exports
def cuota_state(c: Installment, payments: list[Payment], promise: date | None,
                cadence: Cadence, today: date, tol: Tolerance) -> CuotaState:
    active = [p for p in payments if p.status == "active"]
    paid_uf = sum(p.amount_uf for p in active)
    if c.voided_by_endorsement_id:                     return CuotaState("anulada")
    if paid_uf >= c.gross_amount_uf - tol.uf:           return CuotaState("pagada", evidence=max_evidence(active))
    flags = {"parcial"} if active else set()
    if c.direct_debit_rejected_at and (not active or c.direct_debit_rejected_at > max(p.paid_on for p in active)):
        flags.add("rechazada_pac")
    if promise and promise >= today:                    return CuotaState("en_acuerdo", flags)
    if today > c.due_date + timedelta(days=cadence.last): return CuotaState("riesgo_termino", flags)
    if today > c.due_date:                              return CuotaState("vencida", flags)
    if today == c.due_date:                             return CuotaState("vence_hoy", flags)
    return CuotaState("por_vencer", flags)
