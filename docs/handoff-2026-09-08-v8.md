## 1. The reframe (read first — it inverts part of v6/v7)

The meeting established that the broker journey is a sequence of **expedientes** the broker creates at
each milestone, and that **ramos are advisory, not structural**:

- **Group → grupo-cuenta (account/lead) → antecedentes → bases técnicas → comparación → propuesta →
  pólizas → vigente.** Each milestone is a `case_file`-anchored artifact (the `record_expediente`
  satellite pattern, applied uniformly: a thin table linked to the case, typed columns for what's
  sorted/summed + a JSON payload for the dynamic tail + provenance FKs; child tables only where a
  comparator aligns rows).
- **Ramos are aesthetic templates for the antecedentes stage only.** A ramo (`line_record_schema`)
  owns recommended files + explanations + a suggested field shape that primes the AI and lays out Bases
  Técnicas. We seed the templates; a broker may adopt/edit or create a custom one with no guidance.
  Downstream (comparison, policies) is **fully dynamic** and never ramo-structured. `insurance_line`
  stays a separate CMF classifier; the two were **not** merged (the classifier is load-bearing).
- **Antecedentes is warn-not-block.** Free upload always works; Bases Técnicas always renders (as a
  BORRADOR/INCOMPLETO with the missing fields flagged) — the old `GET …/pdf` 409-when-incomplete is gone.
- **Comparison is incremental + dynamic.** Cotizaciones are uploaded one at a time; each is extracted
  dynamically (a fixed money core + an open facet list, no shared field set), wrong files are detected
  and rejected in-place, and an alignment pass builds a COMMON + EXTRAS grid over a **monotonic** canonical
  dictionary so earlier columns never drift as new proposals arrive.
- **Policies are validate-then-dynamic.** An uploaded file is validated against a fixed minimal core
  (corredor / datos asegurado / vigencia / desglose de prima) to confirm it is a policy; then the rest is
  extracted dynamically and kept whole. Many policies per account → an overview + per-policy inspector +
  open-original.
- **Extraction is context-aware.** Policy extraction prepends the account's prior antecedentes / accepted
  proposal, so it reads with context rather than raw.

## 2. Confirmed decisions (from the meeting / this session)

1. **Ramos: real repurpose accepted** (migrations + risk). `line_record_schema` becomes the advisory
   ramo; `insurance_line_id` nullable; `insurance_line` classifier untouched (no merge).
2. **Comparison incremental architecture:** cache per-proposal dynamic extraction, then monotonic
   alignment over the cached compact facets (NOT a single multi-doc call each upload — that re-reads
   everything, blows the window past ~4 proposals, and drifts).
3. **Alignment engine:** AI semantic alignment with a **deterministic slug-match fallback** (keeps the
   test suite hermetic; deterministic-only would fail to line up differently-worded equivalents).
4. **Policy core gate:** hard reject (`not_a_policy` 422) **with an explicit `override`** — no dead end.
5. **Propuesta:** its own `broker_proposal` table anchored to the account `case_file` (not a new
   `CaseFileKind`; and never named `Proposal`, which is the insurer's inbound offer). Direction is
   broker→insurer, built solely from the comparison snapshot; ratification is manual for now.
6. **Public insured decision:** the share surface projects all open proposals (commission stripped) and
   the insured selects via an unauthenticated, idempotent write endpoint; it records the choice only and
   does not auto-advance the stage (the broker mints the propuesta, which advances it).
7. **Journey:** enlarged, at overview altitude, 7 nodes, fed by pending-actions; a default Summary tab.
8. **Demo:** empty-state now; seed later if a fuller walkthrough is wanted.
